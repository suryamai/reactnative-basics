YumQuick v3 – UI/UX Redesign, Navigation, Location &amp; Remaining APIs React Native + Expo + TypeScript · FastAPI backend · Redesign specification 1. Goal of This Update The current build has all the main screens, but it behaves like a set of separate pages. v3 turns it into a proper mobile app: a persistent bottom navigation bar, a location-aware experience (detect location, change it any time, show only what is deliverable there), a consistent modern UI, and the backend APIs still missing to support it. What changes in v3 Bottom tab navigation with a cart badge and a clear active state. Location detection, a location picker with search and map pin, saved addresses, and a header location chip on Home. A full UI/UX refresh: spacing, cards, motion, loading and empty states, and dark mode. Restaurants and location-based menus (nearby, delivery time, delivery fee, serviceability). A complete list of remaining backend APIs (section 9). Note on currency:  the doc and sample data use  $1.99  and 8% tax, but the dishes are Indian. Move currency, delivery fee and tax into a config ( src/constants/config.ts ) and display ₹ by default. 2. Location-Based Experience 3.1 User journey First launch after login:  a friendly permission screen (&quot;Allow location to find food near you&quot;) with two buttons:  Use current location  and  Enter location manually . Allowed:  read GPS, reverse-geocode to an address, check serviceability, save it as the active location, and go to Home. Denied or unavailable:  open the picker for manual entry. Never block the app: allow browsing with a default city. Home header:  shows a location chip — pin icon, label (&quot;Home&quot; or area name), a one-line address and a down chevron. Tapping it opens the picker as a bottom sheet. Changing location:  the picker offers search with suggestions,  Use current location , saved addresses, and  Pick on map  with a draggable pin. Confirming updates the app instantly and refreshes restaurants, dishes, delivery fee and ETA. Not serviceable:  show an illustrated empty state (&quot;We don&apos;t deliver here yet&quot;) with  Change location  and  Notify me when available . Cart conflict:  if the location changes while the cart holds items from a restaurant that doesn&apos;t deliver to the new address, show a dialog to keep or clear the cart. 3.2 Location picker screen Element Behaviour Search field Debounced 300 ms address and area autocomplete, clear button Use current location Requests permission, shows a spinner, fills the address Saved addresses Home, Work, Other with icons, edit and delete swipe actions Pick on map Map with a centered pin; address label updates when the pan ends Address form House / flat, street, landmark, pincode, label chips (Home, Work, Other), contact number Confirm button Fixed at the bottom; disabled until the location is valid and serviceable 3.3 Where location is used Home: nearby restaurants, delivery time and fee, &quot;Popular near you&quot;. Search: results filtered by restaurants that deliver to the active address. Cart and Checkout: delivery address, distance-based fee, ETA. Tracking: destination marker and driver position on a map. Profile: manage saved addresses. 3.4 Technical approach Packages:  expo-location  for permission, GPS and reverse geocoding, and  react-native-maps  for the map and pin. locationStore  (Zustand + AsyncStorage):  { activeAddress, lat, lng, city, pincode, serviceable, permissionStatus } . Use balanced accuracy for speed. Cache the last known position and avoid re-requesting GPS more than once per session start. Prefer the backend for reverse geocoding and autocomplete so the map provider key stays off the device; fall back to  expo-location  reverse geocoding. Send  lat  and  lng  as query parameters to restaurant and menu requests, or pass the active  address_id . Permissions: Android  ACCESS_FINE_LOCATION  and  ACCESS_COARSE_LOCATION ; iOS  NSLocationWhenInUseUsageDescription . Handle &quot;denied forever&quot; with a button that opens system settings. 4. Gaps in the Current Backend Contract The current document lists these issues that must be fixed before the redesign works end to end: Orders accept a single dish.   POST /orders  takes  customer_name ,  item_id ,  quantity . A real cart needs multiple items, add-ons, portion size, notes, address, payment method, promo code and a server-calculated total. No restaurant concept.  Home shows &quot;nearby restaurants&quot;, but there is no restaurants endpoint or restaurant id on menu items. No location awareness.  Menu and orders ignore the user&apos;s position and address. Auth is basic.  There is no refresh, logout, password reset or profile endpoint, although the app uses tokens, biometrics and a profile screen. The documented &quot;16 endpoints&quot; list contains 14 rows  (13 originals plus  /promos/validate ); keep the count in sync after this update. Admin routes need protection  (menu POST / PATCH / DELETE and order status PATCH) with role checks. 8.
